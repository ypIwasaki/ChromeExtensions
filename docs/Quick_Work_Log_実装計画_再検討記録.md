## 2. 評価

JavaScript、HTML/CSS、Manifest V3、ビルド必須でない構成、独自サーバーなしという方針は、小規模な個人用拡張機能と整合する。フレームワーク、汎用状態管理、汎用移行基盤の追加を必要とする根拠は現状ない。

ただし、現計画のままでは仕様の細部を完了条件から漏らし得る。特に外部認証の検証時期、色取得とカテゴリUIの依存、登録の安全性、ポップアップの寿命を先に整理する必要がある。Service Workerの「将来の共通処理の受け口」という説明だけでは責務が定まらず、仕様22章の先行拡張禁止とも整理が必要。

## 4. 改訂の段階構成（基本順序はA2で合意）

1. 既存リポジトリ内の配置、開発環境、仕様対応表、最小拡張機能を準備する。読み込みと起動が検証可能。
2. 外部依存と画面寿命を検証する。OAuth、ID、一覧・色、認証中の閉鎖・復帰を確認し、成立しなければ後続UIへ進まない。
3. 保存・カテゴリ・入力検証を実装する。保存形式とAPI色を含むカテゴリ操作を自動試験と実画面で検証する。
4. 入力から登録までを一貫して実装する。排他、送信値の固定、成功後保存、部分失敗、結果不明も同時に検証する。
5. 異常系・復帰・互換性・アクセシビリティを横断検証する。通常の結合確認をここまで延期しない。
6. 実Chrome・実カレンダーで受け入れ、導入再現、結果と既知制約を記録する。

テストランナー等は必要な機能に応じて最小構成を選ぶ。今は製品を追加しない。実行していない試験を成功扱いにしない。

## 8. 公式資料で確認した技術的前提

確認日: 2026-09-18。実機の成立確認はまだ行っていない。

- [Chrome popup](https://developer.chrome.com/docs/extensions/develop/ui/add-popup): ポップアップ外へフォーカスを移すと閉じ、クリックで閉じる挙動は抑止できない。計画の「不用意なフォーカス移動を避ける」だけでは閉鎖対策にならない。
- [Service Worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle): 非活動や長時間処理等で停止し、グローバル変数は失われる。単なるメモリ上のフラグで再起動をまたぐ保証はできない。
- [Colors.get](https://developers.google.com/workspace/calendar/api/v3/reference/colors/get): 仕様5.3の calendar.calendarlist.readonly は許可スコープに含まれる。色取得のための広い追加スコープは不要。
- [CalendarList.list](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list): ページングとアクセス権フィルターがある。全件取得と画面再取得を混同せず試験する。
- [Identity API](https://developer.chrome.com/docs/extensions/reference/api/identity): 対話認証は利用者操作で開始する。仕様10章と整合。
- [Manifest key](https://developer.chrome.com/docs/extensions/reference/manifest/key): 拡張機能IDの管理方法を初期検証で確認する。
- [Chrome Storage API](https://developer.chrome.com/docs/extensions/reference/api/storage): storage.sessionはメモリ上に保持され、ブラウザー再起動だけでなく拡張機能のリロード・更新・無効化でも消える。A3を満たす範囲と例外を明記する必要がある。
- [JavaScript Date](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Date): ローカル時刻が2回存在する場合は先の時刻が選ばれる。存在しない時刻は自動補正されるため、仕様の拒否条件は別途検証が必要。
