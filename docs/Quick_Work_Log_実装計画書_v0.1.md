# Quick Work Log 実装計画書

- 文書バージョン: v0.1
- 作成日: 2026-09-18
- 対象要件: `Quick_Work_Log_要件定義書_v0.2.md`
- 対象: 初回版
- 開発方式: 機能単位・Issue駆動

## 1. 計画の目的

「Quick Work Log」の初回版を、確認可能な小さな実装単位へ分割し、実装順序、成果物、完了条件、依存関係を明確にする。

各フェーズは、原則として一つ以上のGitHub Issueへ対応させる。次のフェーズへ進む前に、そのフェーズの完了条件を確認し、未完了事項を残したまま後続機能へ依存させない。

## 2. 開発方針

### 2.1 基本方針

- Chrome拡張機能はManifest V3で実装する。
- 初回版はデスクトップ版Google Chromeだけを対象とする。
- 個人がローカル環境へ「パッケージ化されていない拡張機能」として読み込んで使用する。
- Chromeウェブストアへの公開および他者への配布は行わない。
- Googleカレンダーの画面を開かず、Google Calendar APIで予定を登録する。
- 独自サーバーおよび独自データベースは使用しない。
- 閲覧ページの情報は使用しないため、コンテンツスクリプトは導入しない。
- 実装対象外の機能を先回りして追加しない。

### 2.2 技術構成

| 項目 | 採用方針 |
| --- | --- |
| 言語 | JavaScript |
| UI | HTML、CSS、JavaScript |
| 拡張機能形式 | Chrome Extension Manifest V3 |
| 認証 | Chrome Identity APIとGoogle OAuth 2.0 |
| 外部API | Google Calendar API v3 |
| ローカル保存 | `chrome.storage.local` |
| バックグラウンド処理 | Extension Service Worker |
| ビルド | 初回版では必須にしない |
| パッケージ管理 | npm（テスト・静的検査などの開発用途） |
| 単体テスト | JavaScript向けテストランナーを導入する |
| 配布 | ローカル読み込みのみ |

フレームワークは導入せず、Chrome拡張機能の基本構造とWeb標準APIを学べる小規模構成を採用する。テストランナーと静的検査の具体的な製品は、プロジェクト初期化時に対応中のNode.jsで安定して動作するものを選び、READMEとロックファイルへ固定する。

### 2.3 実装上の責務分離

- 表示とユーザー操作
- 入力値の検証
- カテゴリ管理
- 設定・前回値の保存
- Google認証
- Calendar API通信
- APIエラーの分類と画面表示

UIからGoogle APIを直接呼び出す構造にせず、責務ごとのモジュールを介して処理する。

## 5. フェーズ別実装計画

### フェーズ0: 開発準備・外部設定

### 対象

開発開始に必要なリポジトリ、ツール、Google Cloud側の準備を整理する。

### 作業内容

1. `quick-work-log` リポジトリを作成する。
2. Node.jsとnpmの利用バージョン方針を決める。
3. `package.json`、ロックファイル、`.gitignore` を作成する。
4. テストと静的検査を実行するnpmスクリプトを用意する。
5. Google Cloudプロジェクトを作成または選択する。
6. Google Calendar APIを有効化する。
7. OAuth同意画面を個人利用向けに設定する。
8. Chrome拡張機能用のOAuthクライアントを作成する手順をREADME下書きへ記録する。
9. OAuthクライアントIDをソース管理でどう扱うかを決める。

### 成果物

- リポジトリの初期構成
- `package.json`
- ロックファイル
- `.gitignore`
- READMEの初期設定章
- Google Cloud設定手順の記録

### 完了条件

- 新規取得したリポジトリで依存関係を再現できる。
- テストおよび静的検査の空実行またはサンプル実行が成功する。
- Google Calendar APIが有効になっている。
- OAuthクライアント作成までの手順が第三者ではなく、将来の自分が再現できる粒度で記録されている。
- 秘密鍵やアクセストークンがGit管理へ含まれていない。

### 注意事項

拡張機能IDが確定してからOAuthクライアント設定が必要になる場合があるため、Google Cloud上の最終設定はフェーズ1の拡張機能読み込み後に完了させてよい。

### フェーズ1: 拡張機能の最小構成

### 対象

Manifest V3の最小構成と、予定入力画面を開く導線を実装する。

### 作業内容

1. `manifest.json` を作成する。
2. 拡張機能名を「Quick Work Log」とする。
3. ツールバーアイコンと仮のポップアップ画面を登録する。
4. `_execute_action` コマンドへ既定キー `Alt+Shift+C` を設定する。
5. Service Workerの最小構成を作成する。
6. Chromeの拡張機能管理画面からローカル読み込みする。
7. ショートカット競合時の確認方法をREADMEへ記録する。

### 成果物

- `manifest.json`
- `src/background/service-worker.js`
- 仮の `popup.html`、`popup.css`、`popup.js`
- 必要なアイコンファイル
- ローカル読み込み手順

### 完了条件

- Chromeが拡張機能をエラーなく読み込める。
- ツールバーアイコンからポップアップを開ける。
- `Alt+Shift+C` から同じポップアップを開ける。
- ポップアップを開いた直後に仮の先頭入力要素へフォーカスが移る。
- 全Webサイトへのアクセス権限やコンテンツスクリプトを含めていない。

### フェーズ2: データ保存・カテゴリ管理

### 対象

外部APIに依存しないローカルデータ管理を先に完成させる。

### 作業内容

1. `chrome.storage.local` の読み書きをラップする保存モジュールを実装する。
2. カテゴリデータの形式を定義する。
3. カテゴリの一覧取得、追加、編集、削除を実装する。
4. カテゴリ名の前後空白除去と重複判定を実装する。
5. カテゴリ削除の確認処理を実装する。
6. 前回のカレンダーIDと場所を保存・取得する処理を実装する。
7. 初回状態ではカテゴリを0件とする。
8. 保存処理を単体テストできるようChrome APIへの依存を分離する。

### 成果物

- `storage.js`
- `categories.js`
- カテゴリ管理ダイアログの基本UI
- カテゴリと設定の単体テスト

### 完了条件

- カテゴリを追加し、ポップアップを閉じて再度開いても残っている。
- カテゴリ名と色IDを編集できる。
- 削除確認後にカテゴリを削除できる。
- 空欄名、空白だけの名前、同一名称、大文字・小文字だけが異なる名称を登録できない。
- 選択中カテゴリを削除した場合、選択状態が解除される。
- 初回起動時にカテゴリが自動作成されない。
- 単体テストが成功する。

### フェーズ3: 予定入力UI・入力検証

### 対象

予定登録に必要な入力画面と、API呼び出し前の検証を実装する。

### 作業内容

1. 作業名を実装する。
2. 開始日・開始時刻・終了日・終了時刻を実装する。
3. 作業内容・メモを実装する。
4. 登録先カレンダーの仮選択欄を実装する。
5. 場所を実装する。
6. 作業カテゴリ選択欄とカテゴリ管理導線を統合する。
7. 開始日と終了日の初期値を端末の当日に設定する。
8. 開始時刻と終了時刻は空欄で表示する。
9. 前回の場所を初期表示する。
10. 必須項目と日時前後関係の検証を実装する。
11. 項目ごとのエラー表示と全体エラー表示の役割を整理する。
12. Tab移動順と初期フォーカスを調整する。

### 成果物

- 完成形に近い予定入力画面
- `validation.js`
- 入力検証の単体テスト

### 完了条件

- 要件定義書にあるすべての入力項目が表示される。
- 必須項目と任意項目を識別できる。
- 当日の日付と空欄の時刻が正しく初期表示される。
- 終了日時が開始日時以前の場合に登録処理へ進まない。
- 日をまたぐ正しい日時を許可する。
- エラーが対象項目の近くへ表示され、色だけに依存しない。
- キーボードで全項目を順番に操作できる。
- 入力検証の単体テストが成功する。

### フェーズ4: Google認証・カレンダー取得

### 対象

Googleアカウント認証と、予定を書き込めるカレンダー一覧の取得を実装する。

### 作業内容

1. ManifestへOAuthクライアントIDと必要スコープを設定する。
2. Chrome Identity APIを使用した認証処理を実装する。
3. 未認証時の対話的認証を実装する。
4. 無効な認証情報の破棄と再認証処理を実装する。
5. Calendar APIからカレンダー一覧を取得する。
6. 書き込み可能なカレンダーだけを抽出する。
7. カレンダー名の昇順で並べる。
8. 入力画面を開くたびに一覧を取得する。
9. 取得中表示、空一覧、認証失敗、通信失敗を表示する。
10. 前回選択したカレンダーが現在も利用可能なら初期選択する。

### 成果物

- `auth.js`
- `calendar-api.js` のカレンダー一覧取得部分
- 認証・再認証UI
- カレンダー選択UIとの結合

### 完了条件

- 初回認証を完了できる。
- 認証後、書き込み可能なカレンダーだけが名前順で表示される。
- ポップアップを開くたびにカレンダー一覧を再取得する。
- 前回カレンダーが存在すれば選択される。
- 前回カレンダーが存在しない、または書き込み不可なら未選択となり、通知される。
- 認証を取り消した状態で再認証を案内できる。
- 認証情報を通常ログや画面へ表示しない。

### フェーズ5: 色取得・予定登録

### 対象

Googleカレンダーの予定色取得と、予定登録の主要処理を実装する。

### 作業内容

1. Calendar APIから利用可能な予定色を取得する。
2. すべての予定色をカテゴリ編集UIへ表示する。
3. 色名または識別可能なラベルを色見本と併記する。
4. 入力値をCalendar APIのイベント形式へ変換する。
5. 端末タイムゾーンを取得して開始・終了日時へ設定する。
6. 選択したカレンダーへ予定を登録する。
7. タイトル、日時、説明、場所、色IDを対応する予定項目へ設定する。
8. 任意項目が空欄の場合にも登録できるようにする。

### 成果物

- `calendar-api.js` の色取得・予定登録部分
- API送信用データ変換処理
- Googleカレンダーへの実登録機能

### 完了条件

- Googleカレンダーで利用可能な予定色がすべてカテゴリ作成・編集時に表示される。
- 選択したカレンダーへ予定を登録できる。
- 作業名、開始・終了日時、メモ、場所、カテゴリ色が正しく反映される。
- 任意項目を空欄にして登録できる。
- 日をまたぐ予定が正しいタイムゾーンで登録される。
- GoogleカレンダーのWeb画面が自動的に開かない。

### フェーズ6: 登録後処理・障害対応

### 対象

日常利用で問題となる多重操作、前回値、登録失敗を扱う。

### 作業内容

1. 登録開始時に登録ボタンと関連操作を無効化する。
2. 登録中表示を実装する。
3. 登録成功メッセージを実装する。
4. 成功表示後にポップアップを自動で閉じる。
5. 成功時にカレンダーIDと場所を保存する。
6. 場所が空欄の場合、保存済みの場所も空欄へ更新する。
7. 失敗時はフォーム内容を保持する。
8. 入力、認証、権限、通信、カレンダー利用不可、その他APIエラーを分類する。
9. 各エラーに利用者が次に行う操作を表示する。
10. 登録結果が不明な場合に自動再送しない。

### 成果物

- `errors.js`
- 登録中・成功・失敗表示
- 二重登録防止処理
- 前回値更新処理
- エラー分類の単体テスト

### 完了条件

- 登録ボタンを連続操作してもAPI要求が1回だけ送られる。
- 成功時のみ前回カレンダーと場所が更新される。
- 空欄の場所を登録した次回起動時に場所が空欄になる。
- 成功表示後にポップアップが自動で閉じる。
- 失敗時に入力内容が残り、利用者が手動で再実行できる。
- エラー種別と次の操作が表示される。
- 自動再試行を行わない。

### フェーズ7: 結合・非機能対応

2. UIのサイズ、スクロール、入力順を調整する。
3. ラベル、フォーカス、ダイアログ操作、エラー通知を確認する。
4. API待機中の表示と操作禁止範囲を調整する。
5. Manifestの権限を棚卸しする。
6. コンソールログに認証情報や予定本文が出ていないことを確認する。
7. 認証トークンを独自保存または外部送信していないことを確認する。
8. 主要関数へ目的・引数・戻り値が分かる日本語コメントを付ける。
9. 未使用コード、仮表示、開発専用処理を除去する。

### 成果物

- 結合済み拡張機能
- 権限確認記録
- アクセシビリティ確認記録
- コード整理結果

### 完了条件

- キーボードだけで主要操作を完了できる。
- エラーを色だけで表現していない。
- 要件に不要なChrome権限がない。
- 全Webサイトへのアクセス権限がない。
- 認証情報や予定本文が不用意にログ出力されない。
- テストと静的検査がすべて成功する。
- Chrome拡張機能管理画面に実行時エラーが残っていない。

## 8. テスト方針

### 8.1 単体テスト

外部APIやChrome APIから分離できる処理を対象とする。

- 必須項目の検証
- 日時の妥当性と前後関係
- 日をまたぐ日時
- カテゴリ名の正規化
- カテゴリ名の重複判定
- カテゴリ追加・編集・削除
- APIエラーの分類
- Calendar API送信用データへの変換
- カレンダーの名前順整列

### 8.2 結合テスト

- 保存モジュールとカテゴリUI
- 入力フォームと検証処理
- 認証とカレンダー一覧取得
- フォームから予定登録まで
- 成功時の前回値保存
- 失敗時の入力保持

### 8.3 手動テスト

Chrome本体、OAuth、実際のGoogle Calendar APIが関与する項目を対象とする。

- ローカル読み込み
- アイコン・ショートカット起動
- 初回認証と再認証
- カレンダー一覧
- 予定色一覧
- 実際の予定登録
- 通信失敗・権限不足
- ポップアップの自動終了
- キーボード操作

## 9. 実装時の品質基準

- 一つの関数に複数の無関係な責務を持たせない。
- API通信とDOM操作を同じ関数へ混在させない。
- エラーを握りつぶさない。
- 利用者向けメッセージと開発者向け情報を分離する。
- 認証情報や予定本文をログへ出さない。
- 主要関数には目的、引数、戻り値、副作用が分かる日本語コメントを付ける。
- Issueごとに関係するテストを追加または更新する。
- Issueの完了時に、成果物と完了条件を照合する。
- 要件変更が発生した場合は、実装だけでなく要件定義書と本計画書も更新する。

## 10. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| ショートカットがOSや他拡張機能と競合する | 起動できない | Chromeのショートカット設定で変更する手順を案内する |
| OAuth設定と拡張機能IDが一致しない | 認証できない | ID確認後にOAuthクライアント設定を確定する |
| Google Cloudの認証設定が不足する | APIを利用できない | READMEに画面単位の設定手順と確認方法を記載する |
| カレンダーに書き込み権限がない | 登録に失敗する | 書き込み可能なカレンダーだけを表示する |
| API応答が遅い | 入力画面が停止したように見える | 読み込み中・登録中表示を行う |
| 登録結果が不明な通信失敗 | 再実行で重複する可能性 | 自動再試行せず、状態が不明であることを表示する |
| 予定色の仕様差 | 色が期待どおりにならない | APIから色一覧を取得し、固定値に依存しない |
| ポップアップが意図せず閉じる | 入力内容を失う | 登録失敗時は閉じず、操作中の不用意なフォーカス移動を避ける |
| Manifest権限が過剰になる | セキュリティと利用者信頼に影響する | フェーズ7で権限を棚卸しする |
