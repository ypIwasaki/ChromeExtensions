## 1. 改訂理由と対象

既存リポジトリの `quick-work-log/` に個人用Chrome拡張機能を配置する。現在はアプリコード・既存テストがない。リポジトリを作り直さず、文書と版管理を活用する。

外部認証の成立を早く確かめ、色取得とカテゴリUIの依存を直す。最初の実登録から排他・部分失敗・結果不明を扱い、動作するが安全性を欠く中間段階を作らない。計画の完了はIssue番号の消化ではなく、仕様条件と検証結果で判断する。

## 2. 技術構成と責務

JavaScript、HTML、CSS、Manifest V3、Identity API、Calendar API、chrome.storageを使う。UIフレームワーク、独自サーバー、独自DB、ビルド必須化は追加しない。開発用npm依存はテストと静的検査に必要なものだけにする。

| 責務 | 方針 |
| --- | --- |
| ポップアップ | 入力・カテゴリ管理・表示・フォーカス。閉じても送信完了の前提にしない |
| Service Worker | 認証や登録を画面の寿命から分離する実処理の担当とする案。送信の一元管理と再表示への状態提供を担う。常駐保証はしない |
| 純粋処理 | 入力検証、日時生成、送信値変換、カテゴリ重複、並び順、エラー分類 |
| 保存 | 永続データと一時データのアクセスを集約。破損・未知版を自動上書きしない |
| API | 一覧全ページ、予定色、予定登録。DOMを扱わず、トークン・本文をログへ出さない |

画面とWorkerの両方で別々の登録ロックを管理しない。Workerに処理中の要求があるなら再表示でその状態を表示し、Worker停止後に状態だけ残った場合は永遠に処理中とせず結果不明へ移す案とする。具体的なメッセージ形式と保存先はQ8回答後に確定する。

推奨配置は `manifest.json`、`src/popup/`、`src/background/`、`src/modules/`、`tests/` を `quick-work-log/` 内に置く。設計・受け入れ文書は既存のルート `docs/` を利用し、同じ文書を二重管理しない。

5xxやタイムアウトを一律に「未登録」としない。HTTP分類と登録結果の確実性を別に扱う。送信後に応答が得られない場合の試験を必須にする。

保存失敗はエラーを注入して再現し、API成功後に再度POSTしていないことまで確認する。時間と通信は試験で制御し、実APIに依存する試験と分ける。

## 6. 保存・移行・互換性

現行仕様のカテゴリと前回値は永続保存する。下書き・結果表示は一時保存し、同じブラウザー起動中に復元する。ブラウザー再起動・拡張リロード・更新・無効化後の下書き復元は保証しない。APIトークンは独自保存しない。

既存リリースがないため過去版からの移行コードは作らない。保存値が未作成のときだけ初期化し、既存データの破損・未知版は上書きしない。更新時の保持と、拡張リロードによる一時データ消去を試験する。アンインストール後のデータ復元は保証しない。

開発に必要なNode.js・npm・依存の版はF0で選んで固定する。対象Chromeで使うAPIの対応版をF1で確認し、minimum_chrome_versionの必要性を判断する。古いChrome向け互換層は先回りして作らない。実行場所がWSLでも、受け入れの対象は実際に拡張機能を動かすChromeとOSで記録する。

## 7. 仕様変更と未決定事項

合意済みの仕様変更: 下書き・送信状態の再表示、結果不明からの明示操作、色取得失敗時の既存カテゴリ利用と管理停止、破損データの非破壊停止。原仕様書は保持し、改訂仕様または差分文書で確定する。

確定事項: 下書きは同一ブラウザー起動中の範囲で復元する。結果不明は確認結果に応じた3経路で復帰する。海外タイムゾーン・夏時間は初回版の保証対象外。完成基準は機能仕様書と合意差分で自己完結。必須試験環境はWindows版安定版Chrome。

最終レビュー対象の細部: 初回の前回値なしを利用不可エラーと混同しない、非同期取得で入力中フォーカスを奪わない、再表示した成功通知だけを理由に画面を自動終了しない。
